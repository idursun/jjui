---
title: Actions and Bindings
description: Define custom actions and key bindings in config.toml or config.lua
---

Actions are named operations. Bindings connect actions to keys. Both can be defined in `config.toml` or `config.lua` — use whichever fits your workflow.

## Defining an action

### In config.toml

Use `[[actions]]` with an inline Lua snippet:

```toml
[[actions]]
name = "copy-change-id"
desc = "copy change id to clipboard"
lua = '''
local id = context.change_id()
if id then
  copy_to_clipboard(id)
  flash("Copied: " .. id)
end
'''
```

### In config.lua

Pass a function directly to `config.action`:

```lua
function setup(config)
  config.action("copy-change-id", function()
    local id = context.change_id()
    if id then
      copy_to_clipboard(id)
      flash("Copied: " .. id)
    end
  end, { desc = "copy change id to clipboard" })
end
```

## Binding an action to a key

### In config.toml

```toml
[[bindings]]
action = "copy-change-id"
key = "Y"
scope = "revisions"
desc = "copy change id"
```

### In config.lua

Either pass binding options directly to `config.action`:

```lua
config.action("copy-change-id", fn, {
  key = "Y",
  scope = "revisions",
  desc = "copy change id",
})
```

Or bind separately with `config.bind`:

```lua
config.bind({
  action = "copy-change-id",
  key = "Y",
  scope = "revisions",
  desc = "copy change id",
})
```

## Binding fields

| Field | Required | Notes |
|-------|----------|-------|
| `action` | yes | Action name or built-in action ID |
| `scope` | yes | Where the binding is active |
| `key` or `seq` | yes | Set exactly one |
| `desc` | no | Label shown in the help/status bar |
| `args` | no | Arguments for built-in actions |

When a custom TOML action is bound to a key in only one scope, the binding fields can be declared directly on the `[[actions]]` block instead of using a separate `[[bindings]]` block:

```toml
[[actions]]
name = "copy-change-id"
lua = '''
local id = context.change_id()
if id then copy_to_clipboard(id) end
'''
key = "Y"
scope = "revisions"
desc = "copy change id"
```

In this form, omit `action`; jjui uses the action's `name` for the generated binding. When `key` or `seq` is set on an action, `scope` is required. Use separate `[[bindings]]` blocks for built-in actions or when one action needs multiple bindings.

`key` accepts a single key or a list of alternatives:

```toml
key = "r"
key = ["up", "k"]
```

`seq` defines an ordered key sequence (chord):

```toml
[[bindings]]
action = "ui.open_revset"
seq = ["g", "r"]
scope = "revisions"
desc = "open revset"
```

## Scopes

A binding is only active while its scope is in the chain of scopes that the focused view builds for each key press. The chain is ordered from innermost to outermost, and a key is looked up in each scope in turn until one handles it.

The revisions view builds the chain from what the cursor is on:

1. `revisions.<kind>` for the focused object (see the table below), followed by `revisions.object`, which holds keys shared by all objects such as `shift+j` / `shift+k` (jump to the next/previous revision with an object of the same kind). Neither is present when the revision itself is focused.
2. `revisions`: verbs that act on the revision such as `squash` and `rebase`.
3. `revisions.nav`: cursor navigation (`j`/`k`, `pgup`/`pgdown`, `home`/`end`, `@`, ace jump). It is shared by the revisions view and by every operation (`revisions.rebase`, `revisions.squash`, `revisions.revert`, `revisions.duplicate`, `revisions.abandon`, `revisions.absorb`, `revisions.set_parents`, `revisions.diff_range`, `revisions.new_between`, `revisions.bookmark_target`), so operations do not bind these keys themselves.
4. `revset` and then `ui`, which is always available.

While an operation or a text input is open, its own scope comes first and usually stops the chain. For example, `revisions.rebase` is followed by `revisions.nav` but not by `revisions`. Focusing a file in the details view switches to the `revisions.details` scope, which hides the scopes above it.

Per-object scopes:

| Scope | Active when the cursor is on |
|-------|------------------------------|
| `revisions.bookmark` | a bookmark (local or remote) |
| `revisions.change_id` | the change ID (also moves into the file list) |
| `revisions.tag` | a tag |
| `revisions.workspace` | a workspace name |
| `revisions.divergent` | the divergent marker |
| `revisions.elided` | the `~ (elided revisions)` marker |
| `revisions.description` | the description |
| `revisions.author` | the author |
| `revisions.timestamp` | the timestamp |
| `revisions.object` | any object other than the revision itself |

The bookmarks view adds two scopes: `revset.bookmarks` while it is shown (next/previous remote, filter, leave), and `revset.bookmarks.remotes` while the cursor is on the remotes line (fetch, push, rename and remove remotes). `ui.overlay` holds the `esc` binding that dismisses flash messages and the help overlay before any other scope sees the key.

For example, to bind `y` to copy the value of whichever bookmark is focused, only in bookmark scope:

```toml
[[actions]]
name = "copy-bookmark-name"
lua = '''
copy_to_clipboard(context.object().value)
'''
key = "y"
scope = "revisions.bookmark"
desc = "copy name"
```

The default keys for every scope are in `internal/config/default/bindings.toml`.

## Rebinding built-in actions

You can bind any built-in action by its action ID:

```toml
[[bindings]]
action = "ui.open_revset"
key = "L"
scope = "revisions"
desc = "revset"
```

All built-in action IDs and their default bindings are defined in `internal/config/default/bindings.toml` in the source repository.

Some built-in actions accept arguments through `args`. For example, inline describe's `accept` action can force the operation when you intentionally want to update an immutable revision:

```toml
[[bindings]]
action = "revisions.inline_describe.accept"
key = "alt+shift+enter"
scope = "revisions.inline_describe"
desc = "force accept"
args = { force = true }
```

## Overriding built-in actions

You can replace a built-in action's behavior entirely by defining an action with the same name as a built-in. Use `jjui.builtin.*` to call the original implementation from your override.

### In config.toml

```toml
[[actions]]
name = "revisions.move_down"
lua = '''
jjui.builtin.revisions.move_down()
flash("Moved down to: " .. context.change_id())
'''
```

### In config.lua

```lua
function setup(config)
  config.action("revisions.move_down", function()
    jjui.builtin.revisions.move_down()
    flash("Moved down to: " .. context.change_id())
  end)
end
```

Both examples override `move_down` to show a flash message with the change ID after each move, while still performing the original navigation via `jjui.builtin.revisions.move_down()`.

By default, `space` checks the focused object (not just revisions) and moves on: down one row for a revision, or to the next object of the same kind otherwise. To restore the previous behavior of jumping to the parent after selecting, override `revisions.toggle_select`:

```lua
config.action("revisions.toggle_select", function()
  jjui.builtin.revisions.toggle_select()
  jjui.builtin.revisions.jump_to_parent()
end)
```

### Default Lua actions

Many of the default object actions are not compiled in; they are `[[actions]]` with Lua in the default config (`internal/config/default/config.toml`). Examples are `revisions.bookmark.push`, `revisions.bookmark.fetch`, `revisions.bookmark.delete`, `revisions.bookmark.forget`, `revisions.bookmark.advance`, `revisions.change_id.push`, `revisions.change_id.force_rewrite`, `revisions.tag.delete`, `revisions.workspace.switch`, `revisions.workspace.forget`, `revisions.workspace.update_stale`, `revisions.divergent.show_all`, `revisions.divergent.abandon`, `revisions.divergent.update_change_id`, `revisions.elided.show_all`, `revisions.description.edit`, `revisions.author.reset`, `revisions.timestamp.reset`, `revisions.show_bookmarks`, `revisions.show_remotes`, `revset.bookmarks.leave` and `revisions.toggle_select`.

They can be overridden by name like any other built-in. Unlike compiled built-ins, they have no `jjui.builtin.*` version to fall back on, so an override replaces the whole behavior. For example, to make `shift+g` push only the focused bookmark and ignore checked ones:

```toml
[[actions]]
name = "revisions.bookmark.push"
lua = '''
jj_async({ "git", "push", "--bookmark", exact(context.object().value) })
jjui.builtin.revisions.refresh()
'''
```
