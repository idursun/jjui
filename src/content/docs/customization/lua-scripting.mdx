jjui exposes a Lua API for custom workflows and UI automation.

For startup configuration wiring (`setup(config)`, `config.action`, `config.bind`), see [config.lua](/jjui/customization/config-lua).

## Quick start

For LuaLS autocomplete and basic type information, run:

```shell
jjui --install-lua-types
```

This installs generated jjui Lua API metadata into your config directory. See [config.lua](/jjui/customization/config-lua#editor-support) for details.

## Define an action

Define a Lua action in `config.toml` and bind it:

```toml
[[actions]]
name = "hello-lua"
lua = '''
flash("Hello from Lua")
'''

[[bindings]]
action = "hello-lua"
key = "ctrl+h"
scope = "revisions"
desc = "hello"
```

## Namespaces

Helper functions and the `revisions`, `revset`, and `context` tables are available both as top-level globals and under the `jjui` namespace — `flash(...)` and `jjui.flash(...)` are the same, and `revisions.edit()` and `jjui.revisions.edit()` are the same.

Other built-in action scopes (`ui`, `diff`, `oplog`, `annotation`, `undo`, `redo`, `choose`, `input`, `command_history`, `file_search`) are **only** available under the `jjui` namespace — e.g. `jjui.oplog.restore()`, not `oplog.restore()`.

Built-in action wrappers are additionally available under `jjui.builtin.*`, which forces built-in resolution and ignores any user-defined overrides for those action names.

## context.*

Read-only access to the currently highlighted or selected item.

| Function | Returns | Notes |
|----------|---------|-------|
| `context.change_id()` | string | Available for revisions and files |
| `context.commit_id()` | string | Available for revisions, files, and commits |
| `context.file()` | string | Only when a file is selected in the details view |
| `context.operation_id()` | string | Only in the oplog |
| `context.object()` | object | The focused [object](#objects); the revision itself when nothing on it is focused |
| `context.checked_files()` | string[] | Files checked in the details view |
| `context.checked_change_ids()` | string[] | Checked revisions or files |
| `context.checked_commit_ids()` | string[] | Checked revisions, files, or commits |
| `context.checked_objects()` | object[] | Checked [objects](#objects), in the order they were checked |

The selection getters read live UI state when called. After a yielding action or
refresh, they reflect the current selection rather than a cached snapshot. This
lets a script refresh the revision list and then act on the selection that is
visible when the refresh completes:

```lua
revisions.refresh()
local commits = context.checked_commit_ids()
if #commits > 0 then
  flash("Selected " .. #commits .. " commits")
end
```

The inline describe editor exposes its current draft through
`revisions.inline_describe.content()`. It returns the text while the editor is
open and `nil` otherwise:

```lua
local description = revisions.inline_describe.content()
if description then
  flash("Draft length: " .. #description)
end
```

The preview size is available through `ui.preview.size()`, which returns the
current size as a percentage:

```lua
if ui.preview.size() == 100 then
  ui.preview.set_size(50)
end
```

These functions are also available through the `jjui` namespace, such as
`jjui.context.checked_commit_ids()` and
`jjui.revisions.inline_describe.content()`.

### Objects

The cursor can move onto anything jjui draws on a revision: its change ID, bookmarks, tags, description and so on. `context.object()` describes the focused one and `context.checked_objects()` lists the checked ones (a bookmark is listed once per revision it is on). Both return tables with these fields:

| Field | Type | Notes |
|-------|------|-------|
| `kind` | string | `"revision"`, `"bookmark"`, `"tag"`, `"author"`, `"timestamp"`, `"description"`, `"file"`, `"commit"`, `"remote"`, ... |
| `value` | string | The text as shown, e.g. the bookmark name or the file path; the change ID for a revision |
| `remote` | string? | Remote of a remote bookmark or tag |
| `conflicted` | boolean? | `true` for a conflicted bookmark |
| `change_id` | string? | Change ID of the revision the object is on |
| `commit_id` | string? | Commit ID of the revision the object is on |
| `remotes` | `{ name, tracked }[]`? | Remotes of a bookmark; `nil` until the tracking state has loaded |
| `all` | boolean? | `true` for the "all" entry on the remotes line |
| `local_only` | boolean? | `true` for the "local" entry on the remotes line |

`exact(name)` quotes a bookmark, tag or remote name as a jj exact pattern, so `exact("main")` returns `exact:"main"`.

```lua
local object = context.object()
if object.kind == "bookmark" and not object.remote then
  jj_async({ "bookmark", "advance", exact(object.value) })
end
```

Many of the default object actions (`revisions.bookmark.push`, `revisions.tag.delete`, `revisions.workspace.switch`, ...) are written in Lua in the default `config.toml`, which makes them good examples to copy from.

## jj commands

| Function | Returns | Notes |
|----------|---------|-------|
| `jj(...args)` | `(output, err)` | Runs synchronously; returns output string and error |
| `jj_async(...args)` | — | Queues a command without waiting; its output or error is shown as a flash message when it completes |
| `jj_interactive(...args)` | — | Opens an interactive terminal for the command |

Args can be passed as individual strings or as a single table of strings.

Scripts are queued: a script started while another one is running waits for it to finish.

`jj_async` does not return command output to Lua or wait for the command before Lua continues. Use `jj` when later Lua code needs the command's output or must run only after it has completed.

## UI helpers

| Function | Returns | Notes |
|----------|---------|-------|
| `flash(text)` | — | Show a short status message |
| `flash({ text, error?, sticky? })` | — | `error = true` styles as error; `sticky = true` keeps it visible |
| `choose(option1, option2, ...)` | string or nil | Show a picker; returns the selected value or nil if cancelled |
| `choose({ options, title?, ordered? })` | string or nil | Table form; press `/` in any choice dialog to open the `filter:` prompt |
| `input({ title?, prompt?, value? })` | string or nil | Show a text input dialog; `value` sets its initial text; returns the entered text or nil |
| `set_theme(name)` | — | Switch the active theme at runtime |
| `copy_to_clipboard(text)` | `(true, nil)` or `(nil, err)` | Copy to system clipboard |
| `split_lines(text, keep_empty?)` | string[] | Split on newlines; strips `\r`; skips empty lines by default |
| `exec_shell(command)` | — | Run a shell command line; yields until done |
| `change_workspace(path)` | `(true, nil)` or `(nil, err)` | Switch the workspace path used by subsequent `jj` commands |

`set_theme(name)` changes the currently active theme immediately. This is exposed to Lua for custom workflows and plugins, but it is not wired to the UI by default, so you need to call it from your own action, binding, or startup logic.

`change_workspace(path)` is also available as `jjui.change_workspace(path)`. It changes the workspace directory for command execution without reloading repo-specific jjui configuration.

## Built-in action API

Every built-in action is exposed as a Lua function via `jjui.<scope>.<action>()`. These dispatch the action into the UI and yield until it is handled, so they compose naturally with other async steps.

In every scope that has a `cancel()` action, `close()` is available as an alias — e.g. `jjui.undo.close()` is the same as `jjui.undo.cancel()`.

Actions that take a single required string arg accept it positionally:

```lua
revset.set("trunk()")
-- equivalent to:
revset.set({ value = "trunk()" })
```
